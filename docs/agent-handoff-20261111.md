# 项目接手：统一文献库与当前进度

更新日期：2026-11-11。本文供新智能体快速接手；具体实现与状态以运行代码、数据库和下述报告为准。不要把已有阶段成果误认为统一工作已完成。

## 用户当前要求

- 优先统一文献站“作品”和“典籍”：读者使用一个文献入口，按作品、人物、典籍目录等方式浏览；一篇作品拥有统一身份，可关联多个文本版本、典籍位置、译注与有据的行迹引用。
- **以线上 PostgreSQL 为数据整理的依据**；不再维护本地 SQLite，不再逐条修补两套重复正文。可淘汰的重复数据和脚本，在确认引用迁移、备份及可回退后清理。
- 诗词名篇优先使用现有宋词、唐诗语料；缺篇或质量问题再寻源。可读性和可靠来源优先。AI 内容明确标示生成及审校状态，不能冒充古籍或确定事实。
- 零构建、不新增 npm 依赖。地图站通过 poem-data 生成物驱动；不要直接改上游地图数据。两个仓库工作区均有大量未提交改动，不要覆盖、清空或 `git add -A`。地图仓库推送 main 等于发布，按其 AGENTS.md 确认流程执行。

## 现在实际做到哪一步

地图仓库看板当前首项 R-17，见 [进度](../../jiangshan-xingzhi/docs/progress.md) 和 [看板](../../jiangshan-xingzhi/docs/backlog.md)。当前运行中的系统仍是精选编辑数据与原语料分开；统一作品身份、跨书版本模型、正式数据库迁移和页面入口合并均**尚未完成**。

线上业务库与语料库仍分开。既有作品—诗词及站点候选关联只是过渡，不代表统一模型或人工审校，且原导入流程要求站点引文，不能为没有站点引用的作品伪造关系。具体见 [模型盘点](reports/unified-literary-model-audit-20261104.md) 和 [关联样板](reports/literary-link-pilot-20261104.md)。

地图生成器已支持指定数据库导出的临时输入目录，并以线上当前运行版本做过只读导出和隔离生成；没有切换正式发布。线上库架构与本地新版代码不一致：本地直接导出遇 `corpus_work.place_key` 不存在；旧 JSON 与线上数据库有差异。具体计数、命令和限制见 [数据库地图导出验证](reports/database-atlas-export-20261110.md)。不能因字段缺失就直接在线运行迁移；也不要将48篇对象差异误述为48篇正文错误。

线上文献站 8081 曾部署作品候选对照的题名别称和正文兜底；《望岳》繁体串成另一首诗的问题已修正，摘录和异文说明的已上线范围见 [语料关联报告](reports/sushi-corpus-link-20261109.md)。备份路径、镜像与重建限制以该报告为准；服务容器重建会执行既有 `import_json --keep`，不要未经核实随意重启或重建。

## 下一位执行者先做什么

1. 按两仓库 AGENTS.md 先核对 git status、进度和看板；读取 [操作规则](corpus-operations.md)、[项目定位](project-charter.md)、[模型盘点](reports/unified-literary-model-audit-20261104.md) 和 [导出验证](reports/database-atlas-export-20261110.md)。把用户最新要求放在旧文档的 JSON 唯一真相描述之前理解：数据库驱动是新目标，现有 JSON 生成契约仍未替换。
2. 对线上两库、实际表和应用版本做只读核对；明确作品、版本、典籍卷篇、译注、人物、行迹与现有链接的实际引用。调查 `place_key` 等架构差异，并评估数据量、迁移与回滚；不要因本地代码更新而直接迁移生产库。
3. 形成可执行的统一实体及迁移方案，选现有诗词做端到端样板；明确数据库中哪个字段是正文真相、不同版本与摘录怎样表示，以及旧 ID、证据、AI 译注、链接如何保留。先核现有工具能否复用，避免堆叠一次性脚本。
4. 在隔离环境验证迁移与重复执行、引用及旧链接、同名词牌与异文、简繁一致性、备份回读、性能和地图生成；再按授权在服务器分批实施。两库变更与地图发布状态分别记录。
