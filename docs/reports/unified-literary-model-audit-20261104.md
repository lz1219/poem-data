# 作品、人物、典籍与行迹的数据模型核查

2026-11-04，只读核对线上语料库 `jiangshan`、Django 编辑库 `jiangshan_web`、项目 JSON 与现有接口。本记录是调整建议，不代表关联或迁移已实施；阅读试点继续按 R-13 推进。

## 已核实的现状

- 语料库：38 个书目、8 个版本、2,333 个卷篇、140,832 个段落、88,014 首诗词及 125 个人物。诗词均有 `book_id` 和作者文字，但 `corpus_poem` 没有指向人物的外键；有 21,046 首具 `corpus_poem_origin` 来源关联。卷篇来源关联 405 条、段落来源关联 16,222 条；未关联不能一概视为无来源或已核。
- 编辑库：69 个精选作品、39 个人物、20 条行迹、201 个站点；20 条行迹均有编辑库人物外键，95 站有非空引文。`corpus_work.author_id` 指向编辑人物，`corpus_stop` 关联行迹；站点引文与出处当前为文本，无法仅凭字段保证能定位语料段落。
- 两库人物的 `key` 有 21 个相同且姓名相同。这只是匹配候选，不能自动断言跨库身份完全一致。以作品题名与作者原始字段完全相等做最窄筛选，69 件精选作品中 6 件各有一个诗词候选、63 件无精确候选；筛选未处理繁简、别名、摘录、异名或版本，更不是已核映射率。
- 两库分别有自己的作品／人物／版本表示。PostgreSQL 普通外键不能跨数据库；精选发布内容仍以 poem-data JSON 经审核生成地图，完整语料在原语料库，不能把两个边界混为一谈。
- `text_unit.body` 与 `paragraph.body` 均保存正文，`corpus_poem.body` 另存诗词；目前已有 API 和导入器依赖这些结构，不应简单删除任一列或批量重写全文。`book.title` 有唯一约束，但同名书、不同著者和同名版本仍需消歧，不能以书名相同就合并。
- 现有 `corpus_paragraph_explanation` 只支持段落、正整数来源修订以及 `unreviewed`／`withdrawn`，内容和生成信息为 JSON；其单列外键本身不保证 `paragraph_id` 属于 `unit_id`、版本属于同一书，写入与读取目前由应用校验。现有两条样本已上线；该表不应直接宣布为适用于诗词、非维基来源和人工审校的最终模型。

## 建议的目标模型

**共同标识，分清作品与文本见证。** 对作品、人物、书目和版本确定稳定标识与权威记录；同一作品可在多个集子或版本中出现，而一个史书卷也可包含多个独立作品、条目或段落。关系要能定位具体版本和文本范围，不把标题、作者名或字数相同当作同一作品的充分证明。

建议先做以下增量层（表名是设计候选，不是已存在的表）：

| 关系 | 建议保存 | 用途和边界 |
|---|---|---|
| 人物身份映射 | 稳定人物键、语料库人物 ID、外部 ID、别名、匹配状态和依据 | 连接编辑人物与语料人物；同名、异号与身份争议待核 |
| 作品与文本见证 | 稳定作品键、目标类型与 ID（诗词或卷篇/段落范围）、版本、来源、匹配状态 | 精选作品、诗词语料与典籍全文可对应；摘录必须注明范围 |
| 人物与作品 | 人物、作品、关系类型、依据、状态 | 作者、被提及、编者等区别保存，可保留异说 |
| 行迹／事件与文献 | 稳定行迹与站点标识、作品或具体原文定位、关系类型、证据和状态 | 区分引文出处、记载事件、作品写作地点等；待核不进入确定路线 |
| 解释与修订 | 目标具体文本见证、原文哈希与定位、内容类型、来源、生成和审校信息、修订关系 | 诗词和典籍共用译注原则；译文、注释、赏析各自可缺失和修订，原版变更时失配退出展示 |

关系目标应有可验证的引用：优先使用明确的外键和针对不同对象的关联表；如果兼容多种目标，必须保证目标类型与引用唯一且有效，避免只存一个不能约束真实性的任意 `type + id`。来源的固定标识应支持维基修订、Git 提交和本地来源批次；不能继续把所有来源限定为数字修订号。注释偏移以所据版本原字为准，简繁阅读映射另行验证。

来源和断言区分：正文被某页记载、某人被某书提及、某人亲历某地，是不同类型的关系；引文指向原文并不自动证明年代、地点或亲历。既有研究记录、证据与 AI 推测规范应复用，不能用相似度或 AI 自信度充当证据等级。

## 跨库与发布边界

短期不迁库、不把 8 万余首复制进精选 JSON。语料库负责全文和其版本、解释；精选作品、人物、行迹继续遵循已审查 JSON 发布契约。通过稳定键建立**显式跨库映射**，校验器检查两端存在、来源与匹配状态，生成地图时使用已审查映射。跨库对应不是数据库外键，必须靠导入、生成前校验和失效检查保证，不得声称数据库已强制保证。

是否以后将两库合并或调整写入职责，需先评估部署、维护和恢复流程；当前无证据表明合库是贯通阅读的先决条件。无论保留几套物理库，同一逻辑作品的身份与文本见证须有统一契约，不再各自独立维护无标识副本。

## 分批实施

1. 对照实际 JSON、两库与地图生成契约，先定稳定标识、文本范围、可核来源、跨库映射和修订失配规则；补机器校验和回滚方案，不改旧格式。
2. 用一个可核的苏轼专题贯通人物、作品、诗词见证、相关史料段落和行迹站点；先核匹配和每一关系的证据，再实现互相跳转。不存在的映射显示待核，不根据名字或题名批量写入事实。
3. 扩展解释存储以支持诗词见证、不同来源修订和审校状态，兼容已上线两段；验证旧链接、原文哈希失配和撤回，迁移必须可回滚。
4. 从现有 69 件作品、39 人物、20 条行迹逐批核对，再扩大到全文语料。每批报告匹配、歧义、缺口及人工核查范围；不因要完成关联而复制一套全文。
5. 在关系明确、真实查询后才增加必要索引；批量匹配和准备在服务器离线或暂存进行，保持短事务，不为导入默认移除现有索引、外键或 WAL。

本次无线上结构或数据修改。部署、替换旧读本及地图生成遵守现有审批和数据契约。
